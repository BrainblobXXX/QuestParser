# «День орка» (Orc's Day): книга с проверками способностей

> Опыт разбора книги-игры, в которой нет ни `stamina`/`skill`, ни навыков, ни опыта,
> зато есть четыре способности, проверки `2d6 + способность`, бои-контесты и
> Оркишность. Это первый разобранный пакет, где **проверка — не выбор, а бой — не
> урон по кубикам**. Пакет: `orcsday/`, 108 сцен.

**Источник.** «День орка» (Orc's Day), Travis S. Casey, призёр Windhammer 2008;
перевод quest-book.ru, версия 1.02, 2013. PDF, 23 страницы, 100 параграфов,
`Producer: mPDF 5.6`, копирование текста запрещено.

**Цифры пакета.** 100 глав + 8 служебных сцен = 108; переходов 193 (в том числе
96 отсылок вариантов, 31 `next`, 22 проверки, 14 боёв, 2 ставки); выборов 37;
концовок 4 (`6`, `33`, `99`, `result`); недостижимых 7; `take`-выдач 3 сцены
(7 предметов); 29 сцен с `on_enter`; самопроверка — 1359 проверок, 0 ошибок.

## 1. Источник: PDF без абзацев и с запретом копирования

Две вещи сломали привычный порядок.

1. **`pdftohtml` не открывает файл.** Ответ: `Permission Error: Copying of text from
   this document is not allowed`. `pdftotext` при этом работает, поэтому текст и
   координаты слов берутся им: `pdftotext -bbox` даёт `xMin/yMin/xMax/yMax` каждого
   слова. Аннотаций-ссылок получить не удалось: цели отсылок разбирались из текста
   и проверялись по графу (все сошлись). Случай — `C_SOURCE_PROTECTED`.
2. **В PDF нет абзацных отступов.** `pdftotext -layout` отдаёт ровные строки, и
   «абзац по отступу» (правило 4.2 для mPDF) не срабатывает. Рабочий приём:
   - собрать визуальные строки из слов по `y` (допуск 3 pt), упорядочить по `x`;
   - считать строку концом абзаца, если её правая граница заметно меньше полной
     (порог ~520 pt при поле до 553): следующая строка начинает новый абзац;
   - строка с `* ` или `- ` (реплика) всегда начинает новый абзац;
   - склеивать строки пробелом, **не** трогая дефисы: в этой книге на границах строк
     нет переносов слов, только тире, поэтому правило «дефис без пробела» не
     понадобилось (проверено: 880 визуальных строк, ни одного переноса).
   - отдельно поправить места, где PDF сам разбил одну фразу на строки-абзацы:
     у §93 статблок «Атака 10, / Защита 11, / Здоровье 8.» и строка «4-6 / - ты.»
     собираются в один абзац вручную.

**Проверка полноты.** Номеров страниц в тексте нет (это не колонтитул, а отсутствие
футера); 100 маркеров `1…100` монотонны, без пропусков. Заголовок «Подсчет
результата» в конце книги не имеет номера и по правилу «номер — не секция» не стал
главой: он вынесен в сцену `result`, а §100 ведёт в неё.

**Титул.** Эмблема конкурса — единственное изображение книги; она стала обложкой
(`assets/cover.webp`), баннер сайта обрезан. Кадров внутри книги нет — режим
«без книжных иллюстраций», 21 кадр в `illustrations.md` остаётся планом
(`C_IMAGE_ORNAMENT` для эмблемы, `C_IMAGE_UNMAPPED` не нужен).

## 2. Тип: проверки способностей — ещё не `rpg`

Сигналы книги: лист персонажа (Мышцы, Мозги, Удаль, Удача), Здоровье 5,
Оркишность 6, деньги 20, проверки `2d6 + способность`, бои раундами, расходники,
оружие и броня. Навыков, опыта и торговли нет.

Правило, которое пришлось уточнить в [book-types/index.md](book-types/index.md):
**наличие проверок само по себе не делает книгу `rpg`.** `rpg` — это навыки, опыт,
торговля, проверки по навыкам; проверка способности (`2d6 + Удача`) — это
`fighting-fantasy` с расширением, а не `rpg`. Иначе книга с четырьмя
характеристиками и кубиком уезжает в тип, правила которого ей не подходят.

Тип подтверждён человеком: `type: fighting-fantasy`.

## 4. Проверки: `checks` без кубика

Нормативная схема `checks` — `scene`, `stat`, `compare`, `success`, `failure`, где
`compare` сравнивает статус с целым (`< 3`). Книга просит другое: `2d6 + stat ≥
сложность`, причём сложность бывает фиксированной (`10`, `9`, `12`) и динамической
(`Оркишность + 5`, `Оркишность + brains`, `max(brains, luck)`).

**Решение пакета.** Проверка живёт в `mechanics.yaml → checks`, `compare` хранит
книжную формулу строкой (`">= 10"`, `">= orkishness + 5"`,
`">= orkishness + brains"`), сцена с проверкой **не имеет** `next`/`variants`:
выход задают `success`/`failure`. Схема при этом честно расширяется, а не
подменяется: движку нужны `2d6` и выражения в `compare`. Случай —
`C_CHECK_UNSUPPORTED` (системная строка на 22 сцены).

**Проверки внутри вариантов.** Шесть проверок стоят за выбором
(§14, §26, §32, §42, §43, §79): «Чтобы попытаться убить его, сравни свою Удаль…».
Это не чистая проверка: у игрока есть выбор, а проверка решает исход варианта.
Пакет сохраняет выбор (`variants`), а проверку фиксирует в `review.md`: выбран
безопасный целевой исход, второй исход описан в прозе. Превращать такой выбор в
проверку нельзя — теряется решение игрока.

**Проверка с выбором после успеха.** §10: «проверка Мышц 10; если успешно, можно
открыть дверь (3) или уйти (47)». Одна сцена не может быть одновременно проверкой и
`variants`. Решение — техническая сцена `s10_win`: проверка ведёт в неё, а она уже
держит два варианта. То же для §68 (победа → выбор 3/47) и §73 (провал проверки →
бой): `s68_win`, `s73_fight`. Правило: **проверка/бой дают один выход, а выбор
после них — отдельная сцена**; текст переносится, новых слов нет
(`C_CONTENT_ADDED` на ключ, не на текст).

**Состязание вместо проверки.** §55 — цикл «сравни `Удаль + Мозги` с
`Мышцы + Оркишность + 5`; выиграл — минус Оркишность, проиграл — минус Удаль; кто
первым дошёл до нуля». Это не один бросок. Пакет встраивает упрощённую проверку в
три вызывающие сцены (§30, §37, §75), а §55 оставляет страницей-правилом: иначе
теряются разные исходы у разных вызывающих (`C_MECHANICS` + `C_CALL_RETURN_UNSUPPORTED`).

**Ещё ловушки:**
- «проверь Мозги или Удачу (смотря что выше)» — одна проверка, но стат выбирается
  максимумом; в `checks` стоит один стат, `max(stat, stat)` — в отчёте;
- «проверь Оркишность со сложностью 12» — проверяемый стат сам может быть
  Оркишностью; это нормально, но `compare: ">= 12"` складывается с `2d6`;
- проверка без числа («проверьте Удачу») — не сюда, это `C_CHECK_PROSE`/`C_CHECK_UNSUPPORTED`.

## 5. Бои: Атака — это сложность, а не урон

Схема `combat` рассчитана на Fighting Fantasy: `attack` — сколько снимает каждый
выживший за раунд, `health` — здоровье врага, `weapon` — id оружия с `damage`-
кубиками. В «Дне орка» всё иначе:

- противник атакует первым: `2d6 + max(Мозги, Удача) + броня ≥ Атака`, иначе −1 Здоровье;
- игрок атакует: `2d6 + Мышцы + рейтинг оружия ≥ Защита`, иначе враг теряет 1 Здоровье;
- у врага три числа: **Атака, Защита, Здоровье**; попадание всегда снимает 1.

**Решение пакета (честные числа + блокер).** В `combat` записаны `attack` = Атака,
`defense` = Защита, `health` = Здоровье, `count: 1` (статблок группы один). В
`review.md` — `C_COMBAT_UNSUPPORTED` с приоритетом «блокер»: пока движок не умеет
контестный бой, числа не заработают. Подгонять `attack: 1` (урон за попадание)
нельзя: это скрытая подмена правил; если понадобится — это отдельное решение
человека и отдельная строка отчёта.

**Особые бои:**
- §38 — бой не до смерти: «когда здоровье одного из вас упадёт до единицы, перейди
  на 7». `win: "7"`, `lose` нет; `C_COMBAT_INCOMPLETE`;
- §89 — «независимо от исхода, для тебя это конец истории»: `win` и `lose` ведут в
  `result`; это не ошибка, но и не победа;
- §40/§89/§93/§96 — союзники и спутница меняют Атаку/Защиту и получают урон;
  модификаторы в схеме не выражаются (`C_STAT_AMBIGUOUS`);
- §86 — зелье зомби даёт авто-победу после проверки Мозгов; это `C_CHECK_PROSE`
  в прозе, не выбор;
- §5/§11/§20 — подход к §91 с разными модификаторами («орки помогают, вычти 2 из
  Атаки/Защиты»); модификатор живёт в прозе, а не на ребре (`C_STAT_AMBIGUOUS`).

## 6. Создание персонажа: счётчик и разностные статусы

Книга: «десять очков на все способности, распредели как угодно, сумма ≤ 10», а
Оркишность зависит от итогового распределения. В формате нет ввода чисел — только
выборы. Рабочая схема:

1. стартовая сцена `intro` (правила) → `create` (распределение) → `create_done`
   (правила Оркишности и старт §1);
2. `create` — самоцикл: четыре варианта «+1 к способности» с
   `if: stat creation_points > 0` и `stat: {muscles: 1, creation_points: -1, …}`,
   плюс «Закончить распределение» → `create_done`;
3. `creation_points` — статус `initial: 10, min: 0, max: 10, show: false`;
4. чтобы выразить «Мозги круче Мышц», «сильнейшая — Мышцы», «Удаль выше Мозгов»,
   заводятся **разностные статусы**: `d_bm = brains − muscles`, `d_gb = guts − brains`,
   `d_mg = muscles − guts`, `d_ml = muscles − luck`; каждый «+1» двигает и их;
5. `create_done` применяет шесть правил Оркишности через `on_enter` с `if` на
   разностях — это статические дельты, движку ничего нового не нужно.

Цена: пять служебных статусов; MVP игнорирует `show: false`, поэтому они видны
(`C_MECHANICS_ADDED`); отрицательные значения способностей недостижимы (только
`+1`), поэтому правило «если способность отрицательна — минус 1» остаётся мёртвым;
ничьи в «сильнейшая — Мышцы» трактуются как «Мышцы». Всё это — в отчёт.

**Правило на будущее.** Если книга даёт игроку распределять очки, а формат не умеет
ввода — это сцена-цикл со счётчиком; если правила зависят от сравнения статов —
разностные статусы, а не `if: stat a > stat b` (такого предиката нет).

## 7. Спутница: ветка, которая стала недостижимой

§40 и §96: победа зависит от здоровья девушки (3): жива → 85, погибла → 21; §21
ведёт в 92 (спасти) или 64 (дать умереть), §64 → 50 или 20. Схема `combat` знает
только `win`/`lose`, здоровья спутницы и выбора цели в ней нет.

Пакет выбирает основной путь (`win: 85`), а ветка 21 → 64/92 → 50 остаётся
недостижимой. Человек подтвердил: оставить как есть. Код —
`C_COMPANION_UNSUPPORTED` (новый), плюс `W_SCENE_UNREACHABLE` на 21/50/64/92.
Заводить `bethany_hp` без механики спутницы бессмысленно: статус некому менять.

**Урок.** Перед разметкой боя ищи в прозе не только числа врага, но и **второго
участника**: здоровье, выбор цели, «если она погибла». Если он есть — ветка
недостижима, и это надо сказать человеку до сборки, а не после.

## 8. Предметы: рейтинг — не `damage`

`damage` в `items.yaml` — формула броска (`1d6+2`), а в книге «рейтинг оружия +2»
прибавляется к `2d6 + Мышцы` при проверке. Это не урон-кубик: писать
`damage: "1d6+2"` — выдумка. Рейтинги и «три применения палочки» остаются
описанием, случай — `C_ITEMS_UNTRACKED` / `C_STAT_AMBIGUOUS`.

Что всё-таки смоделировано: выдачи (`take` в `on_enter` §22, §43, §51), стартовый
инвентарь (`start_items`), зелья с `restore: hp` (лечат до максимума, а книга —
«+3, не выше 5»: приближение, отмечено). Зелье Беттани — сюжетное, приходит и
тратится внутри боя; в инвентарь не заводится (`C_ITEM_NO_SOURCE`).

## 9. Ставки: `gambles` как расширение

§15/§24/§97: ставка 1–5 серебра, `2d6 + Удача`, три полосы (15+ — ставка + столько
же; 12–15 — ставка; меньше — потеря). Ни `stat` (дельты константны), ни `next.roll`
(нет модификатора), ни `checks` (только success/failure) этого не выражают.
Предложен блок (в пакете он есть, в нормативную схему пока не входит):

```yaml
gambles:
  - scene: "97"
    stat: luck
    stake: {min: 1, max: 5}
    win: 15          # 15+ → ставка + столько же
    push: 12         # 12–14 → ставка
    # меньше push → ставка потеряна
```

Семантика: игрок вводит ставку, движок бросает `2d6 + stat`, сравнивает с
`win`/`push`, меняет `money`. В §24 после ставки остаётся проверка Мозгов — порядок
«сначала `gambles`, потом `checks`». Риски: неизвестное поле в `mechanics.yaml`
(`E_MECHANICS_UNKNOWN_FIELD`), перекрытие полос в §97 на 15 (принято `win: 15`,
`push: 12`), две механики в одной сцене §24.

Случай в отчёте — `C_GAMBLE_UNSUPPORTED` (до расширения) и `C_MECHANICS_ADDED`
(после).

## 10. Страницы-подпрограммы и возврат «к вызвавшей сцене»

§33: «получи имя… вернись к параграфу, с которого перешёл сюда». §55: «выполни
инструкции на 33, затем перейди на тот параграф, с которого попал сюда». §65:
«когда Оркишность упадёт до нуля, перейди на 33». Формат не умеет call/return:
у сцены один выход, и он не зависит от того, кто её вызвал.

**Решение.** Вызовы §55 встроены в §30/§37/§75 (у каждого свои success/failure);
§33/§55/§65 остаются helper-страницами и недостижимы; §65 ведёт в 33, §33 —
концовка-тупик (`C_SCENE_DEAD_END`). Ссылки «перейди на 65, затем вернись сюда» из
§8/§21/§34/§98 удалены как адресные (`C_DYNAMIC_LINK`). Флаг `named` не заводится:
§33 недостижима, и флаг неоткуда взять без триггера «Оркишность ≤ 0».
Код для этого класса — `C_CALL_RETURN_UNSUPPORTED` (новый).

**Урок.** Страницу-подпрограмму нельзя оставлять линейной сценой «в середине»:
либо встраивай её исходы в вызывающие сцены, либо оставляй helper-страницей и
честно пиши, что она недостижима.

## 11. Текст, граф и финал

- **Маркеры `* `** — не текст, а формат списка: сняты, иначе MVP покажет звёздочки
  (`C_MARKDOWN_UNRENDERED`). Реплики `- ` сохранены.
- **Чисто адресные строки** удалены целиком («Перейди на 8.»), смысловые — только
  без адреса («Если нет, ты погиб…» осталось). Итоговые фразы смертей сохранены.
- **Сверка по словам.** Дешевле и точнее «подпоследовательности»: сравнить список
  слов книги и сцены после разметки. В главах 1–100 **ноль вставленных слов**,
  удаления перечислены по сценам; это ловит и потерянную фразу, и случайную
  правку. Вставки допустимы только в служебных сценах (`intro`, `create`,
  `create_done`, `result`) и в подписях кнопок создания персонажа.
- **Финальный экран.** «Подсчет результата» — отдельная концовка `result`;
  смерти и финалы ведут в неё (`next: "result"`). Достижения считаются вручную,
  флаги не заводятся.
- **Проверка с выбором после успеха** — техническая сцена (§4).
- **Недостижимые** — 21, 33, 50, 55, 64, 65, 92; все объяснены в отчёте
  (`C_COMPANION_UNSUPPORTED`, `C_CALL_RETURN_UNSUPPORTED`), ни одна не удалена.

## 12. Чек-лист конвертера для книги с проверками/контестным боем

1. **Источник.** Попробуй `pdftohtml`; при `Permission Error` — `pdftotext` и
   `-bbox`. Нет абзацных отступов — восстанавливай абзацы по коротким строкам,
   проверь переносы и склей разорванные статблоки.
2. **Тип.** Проверки способностей без навыков/опыта/торговли — это
   `fighting-fantasy`, а не `rpg`; подтверди у человека.
3. **Инвентаризация проверок.** Выпиши все: фиксированная сложность, динамическая
   (`Оркишность + N`), `max(stat, stat)`, суммы, проверки внутри вариантов.
   Чистые — в `checks`; внутри вариантов — выбор сохранить, проверку в отчёт.
4. **Проверка + выбор.** Одна сцена — один выход: проверка ведёт в техническую
   сцену с выбором (`s10_win`), а не наоборот.
5. **Бои.** Сначала реши, что такое `attack`: урон за раунд или сложность
   проверки. Если сложность — пиши Атаку/Защиту/Здоровье честно и ставь блокер
   `C_COMBAT_UNSUPPORTED`; не подгоняй под FF.
6. **Спутник.** Ищи здоровье/выбор цели/«если погибла»; ожидай недостижимую ветку
   и подтверди её у человека (`C_COMPANION_UNSUPPORTED`).
7. **Создание.** Нет ввода чисел — сцена-цикл со счётчиком; сравнения статов —
   разностные статусы.
8. **Ставки.** Переменная сумма + полосы + выплата — `gambles` как расширение;
   в отчёт — что именно расширено.
9. **Подпрограммы.** «Вернись туда, откуда пришёл» — встроить в вызывающие сцены
   или helper-страница; `C_CALL_RETURN_UNSUPPORTED`.
10. **Текст.** Снять `* `, удалять только адреса, сверить по словам (ноль вставок),
    смерти и финалы сохранить; финальный экран — отдельная концовка.
11. **Отчёт.** 0 `open`; системные коды — одной строкой с количеством, а не
    30 одинаковых.

## 13. Ловушки, которые стоили времени

| Ловушка | Как правильно |
|---|---|
| «Сравни Удаль с Оркишностью + 5» | это проверка `2d6 + Удаль`, а не выбор; в `checks` — `compare: ">= orkishness + 5"` |
| «Удаль», «Смелость», «Отвага» в одной книге | один стат `guts`; синонимы — в описании/отчёте, не три статуса |
| «Атака 10, Защита 11» у врага | это сложности проверок, а не урон; `attack` в FF-схеме — другое |
| «Три орка: Здоровье 4» | один статблок группы; `count: 1`, а не `count: 3` с health 4 |
| «рейтинг оружия +2» | не `damage: "1d6+2"`; рейтинг — в описание, случай в отчёт |
| «Оркишность» может уйти ниже нуля | `min: -20`, иначе clamp скроет минус |
| «Вычти 2 из Оркишности» в прозе | текст остаётся, эффект — `on_enter`/вариант; это не правка текста |
| «Перейди на 65, затем вернись сюда» | call/return; вызов удалить, страницу — helper |
| «Если девушка погибла → 21» | спутник; ветка недостижима без его здоровья |
| «Если проверка успешна и тебе хочется…» | проверка + выбор: техническая сцена |
| «Начни с параграфа 1» в прозе | номер в прозе запрещён; `next: "1"` и фраза без номера |
| «Подсчет результата» без номера | отдельная концовка `result`, а не потерянный хвост §100 |

## 14. Что осталось открытым

- **Движок.** Нужны: `2d6 + stat` в `checks`, выражения в `compare`, контестный бой
  (`Атака`/`Защита` как сложности), `gambles`, здоровье спутника. Пакет собран так,
  чтобы данные были честными; без движка часть сцен неиграбельна — это блокер,
  а не дефект разбора.
- **`gambles` в нормативной схеме.** Пока это `[предложение]`: поле описано в
  [manifest.md](manifest.md) §2.6 и в этой заметке, но валидатор его не знает.
- **`defense` в `combat`.** Схема FF его не требует, контестный бой — требует;
  поле записано, вопрос к схеме — в `review.md` пакета.
