# ProjectOverall — веб-движок текстовых квестов

## Документ управления проектом

**Версия:** 0.47
**Статус:** рабочий документ

**Роль документа:** отвечает на вопросы «что за проект, куда идём, по каким этапам,
какие решения зафиксированы и что осталось решить».

**Связанные документы:**

- [MVP.md](MVP.md) — дизайн-док первой версии продукта;
- [AGENTS.md](AGENTS.md) — правила, по которым заполняются документы игры (точка входа; старый `QuestRules.md` — указатель на набор).

---

## 0. Набор документов проекта

### 0.1. Разделение ответственности

| Документ | Отвечает за | Не содержит |
|---|---|---|
| **ProjectOverall.md** (этот файл) | идею и цель проекта, модель загрузки контента, дорожную карту, риски, TBD этапа 2, статус, реестр решений | синтаксис игровых пакетов, детализацию механик MVP |
| [MVP.md](MVP.md) | границы MVP, состав работ этапа 1, предзагруженные игры, архитектуру MVP, критерии успеха | планы после MVP, синтаксис формата |
| [AGENTS.md](AGENTS.md) | **исполняемая инструкция для ИИ-конвертации** (§0.4, А.8) + структура пакета, сцены, выборы, условия, эффекты, предметы, статусы, изображения и звук, правила валидатора | управление проектом, состав MVP |

### 0.2. Соглашения

- **Зафиксировано** — решение принято; меняется только новой версией с записью в истории изменений.
- **TBD N** — открытый вопрос. Нумерация сквозная по трём документам:
  - TBD 1–10 — формат игровых пакетов ([AGENTS.md](AGENTS.md), §13);
  - TBD 11 — предзагруженные игры ([MVP.md](MVP.md));
  - TBD 12 — загрузка пользовательской игры (этот файл, §6).
- **[предложение]** — вариант, который ещё не принят.
- **Уровень C** — целевой объём движка, см. §2.2.

## 2. Идея и цель проекта

### 2.1. Что делаем

## 3. Ключевое решение: модель загрузки контента

### 3.1. Решение для MVP

Для первой версии продукта **не требуется** реализовывать полноценную загрузку
пользовательской игры через веб-интерфейс.

В MVP приложение будет поставляться с **предзагруженными играми**.

Это означает:

- пользователь не загружает свой архив или папку через интерфейс;
- пользователь не управляет библиотекой пользовательских игр;
- пользователь не загружает свои изображения, звук и правила через веб-форму;
- в приложении уже есть несколько готовых игр для тестирования и демонстрации.

### 3.2. Решение для второго этапа

Загрузка своей игры через веб-интерфейс приложения — это **второй этап development**.

Этот этап можно назвать:

> **Функциональное демо продукта.**

На этом этапе пользователь уже сможет:

- загрузить свой игровой пакет;
- пройти валидацию;
- увидеть ошибки и предупреждения;
- добавить игру в библиотеку;
- запустить её;
- при необходимости удалить или обновить игру.

### 3.3. Почему это важно

Такое разделение позволяет:

1. Сначала проверить сам формат и игровой движок.
2. Не тратить время MVP на сложный процесс загрузки файлов.
3. Не реализовывать сразу хранение пользовательских ассетов.
4. Не делать сразу управление библиотекой пользовательских игр.
5. Сосредоточиться на качестве игрового опыта.
6. Использовать предзагруженные игры как эталонные примеры формата.

## 7. Риски и ограничения

### 7.1. Предзагруженные игры могут скрыть проблемы загрузки

Если тестировать только предзагруженные игры, можно не заметить проблемы, которые
возникнут при пользовательской загрузке:

- неправильная структура архива;
- отсутствующие файлы;
- неверные пути;
- слишком большие ассеты;
- повреждённые файлы;
- кириллица в именах файлов;
- разные кодировки.

Решение:

- использовать предзагруженные игры как эталонные пакеты ([MVP.md](MVP.md), §4.3);
- заранее готовить тестовые некорректные пакеты;
- проектировать парсер независимо от источника контента;
- на втором этапе отдельно тестировать пользовательскую загрузку.

### 7.2. Формат может быть слишком сложным для авторов

Если формат станет слишком сложным, даже предзагруженные игры будет трудно создавать.

Решение (детализируется в [QuestRules.md](QuestRules.md), §1.4):

- держать MVP-профиль простым;
- документировать формат;
- давать шаблоны;
- использовать понятные имена полей;
- делать валидатор с человеческими сообщениями.

### 7.3. Пользовательская загрузка может потребовать сложной инфраструктуры

На втором этапе могут понадобиться:

- хранение файлов;
- распаковка архивов;
- проверка безопасности;
- лимиты размеров;
- обработка ошибок;
- управление библиотекой.

Решение:

- не включать это в MVP;
- проектировать загрузку как отдельный модуль;
- сначала сделать простой вариант загрузки;
- расширять постепенно.
